> **New research:** LLM coding agents suffer measurable performance collapse as framework conventions accumulate, dropping 30 points between minimal and convention-heavy stacks.

Framework selection has always involved tradeoffs: ecosystem size, hiring pool, documentation quality, community momentum. A paper published this week adds a new axis to that decision. Researchers measured what they call "constraint decay" in LLM coding agents, the pattern where agent accuracy degrades as structural requirements (schemas, ORMs, architectural patterns, dependency injection) accumulate in a codebase. Agents that succeed reliably with minimal frameworks like Flask fall apart when asked to work within convention-heavy frameworks like Django and FastAPI, losing 30 points of accuracy between the two.

The root cause is specific: data-layer defects. Incorrect ORM (object-relational mapper) usage, query composition failures, misapplied model relationships. Convention-heavy frameworks encode behavior implicitly. Django's ORM expects you to know that `select_related` is for foreign keys and `prefetch_related` is for many-to-many. FastAPI's dependency injection expects you to understand the resolution order without it being stated anywhere in the code. These are learned behaviors for human developers. For an agent, they are invisible rules that exist in documentation and training data but not in the code it is currently reading.

Same model, same prompts, same task complexity. The conventions are the variable.

A separate project this week reinforces the other side of the equation. Forge, an open-source agent harness, demonstrated that structural guardrails (response validation, rescue parsing, retry loops) can take an 8B parameter model from single-digit accuracy to 84% on agentic tasks. Applied to Claude Sonnet 4.6, the same guardrails pushed accuracy from 85% to 98%. The variable is the infrastructure around the model.

## Why This Matters for Developers

When evaluating frameworks for a new project, ask: how much of this framework's behavior is implicit? How much relies on conventions the developer (or agent) is expected to already know? Frameworks where behavior is explicit in the code (type annotations, explicit query builders, configuration-as-code) give agents more to work with.

If your team already uses Django or a similar convention-heavy framework, the research points to specific weak spots: data-layer operations. That is where agents produce the most defects. Explicit wrappers around implicit ORM behavior give agents a surface they can actually reason about: typed query interfaces, validation functions, configuration objects that make the implicit explicit.

Forge's results show that a 98% ceiling is achievable with current models when the surrounding system validates outputs, retries on structural failures, and enforces response schemas. If your agent pipeline has no retry logic, no output validation, and no schema enforcement, that is a larger reliability gap than any model swap will close.

For greenfield projects, bias toward explicit-everything architectures: Express with explicit middleware, Hono, Flask with explicit route configuration, Go's standard library, Rust's Axum. Frameworks where the code says what it does rather than relying on the developer to know what it does implicitly.

As agents take on more implementation work, the gap between implicit and explicit frameworks will compound. Teams making stack decisions today are locking in their agent productivity ceiling for the next two to three years.
